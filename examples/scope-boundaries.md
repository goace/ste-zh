# 适用范围示例

本文件说明 [SKILL.md 的适用范围](../SKILL.md#适用范围)，不增加适用场景。先看内容用途，再看交流类型；不能只看长度、是否在开发，或是否包含「方案」「结果」。

## 简单问答与正式汇报

| 用户请求或当前内容 | 是否适用 | 表达方式 |
|---|---|---|
| 「改了几个文件？」 | 不适用 | 直接答「6 个。」不加状态、验证节或自检。 |
| 「提交了吗？」 | 不适用 | 按实际情况直接答「还没有。」或给出提交号。 |
| 「说一下这次改了什么、验证了什么。」 | 适用 | 交代完成范围、改动、验证和遗留事项，见 [结果汇报示例](result-report.md)。 |
| 「还在跑吗？」 | 不适用 | 按实际情况直接回答运行状态。 |
| 主动告知部署阻塞及影响 | 适用 | 例如「阻塞：部署缺少访问权限，发布无法继续。」一句已足够时不展开模板。 |
| 「timeout 是什么意思？」 | 不适用 | 直接解释术语。 |
| 「为什么这次请求超时？查到原因了吗？」 | 适用 | 汇报排查结论、依据及下一步；原因未确定时写明。 |
| 「目录名用哪个？」只需确定一个名称 | 不适用 | 直接确认名称，不强列方案后果。 |
| 需要用户在两种迁移方案中决定，停机时间和回退方式不同 | 适用 | 说明待决事项，比较各方案及其后果。 |

正式汇报后，用户接着问「所以改了几个文件？」，仍直接回答数量。前一条适用，不会使后一条自动适用。

普通知识解释、开放讨论或设计交流不自动归为工作汇报。即使回复很长、讨论技术问题，也不因此应用 STE；只有实际形成表中对应的排查结论或方案决策内容时，该部分才适用。

## 写给 agent 的材料

以下内容均不适用：

- 写入文件的 agent 指令、流程、提示词和参考材料。
- 在聊天中展示、供用户审阅的上述材料草稿，无论是否使用代码块。
- skill 的入口文件、参考文档和草稿。

例如，用户要求「给 agent 写一段执行规则」，草稿可以是：

```markdown
执行前应读取项目约定。
需要改变接口时，先确认兼容要求。
避免覆盖与当前任务无关的修改。
```

这段内容是给 agent 的执行材料，不因展示给用户而成为工作汇报。不得为了 STE 将「应」「需要」「避免」强制替换为受控情态词，也不得套用汇报状态、句长或自检要求。材料的表达由其自身要求决定。

写入项目的文件、代码、注释、commit message 和原样引用也属于排除项。文件面向人阅读，不会取消这项排除。

## 同一条回复包含汇报和草稿

例如，用户要求编写 agent 指令并说明改动：

> 已完成：执行规则草稿，包含修改前的检查和接口变更条件。
>
> 草稿：
>
> 执行前应读取项目约定。需要改变接口时，先确认兼容要求。避免覆盖与当前任务无关的修改。

第一段是向用户交代结果的汇报，适用。草稿正文是给 agent 的材料，不适用；不能因同处一条回复而统一改写。若完整草稿以普通段落展示，判断相同。

## 多项总结与执行提示词

向用户汇总多项需求时，适用，见 [多项需求总结示例](task-summary.md)。将同一批需求写成供 agent 执行的提示词时，提示词不适用。主题相同，材料用途不同，判断也不同。
