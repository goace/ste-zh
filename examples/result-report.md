# 示例：结果汇报

本示例的来源是虚构的。

这是向用户交代改动、原因和验证的工作汇报，符合 [适用范围](../SKILL.md#适用范围)。不是给 agent 编写执行材料的格式，也不要求简单问答使用此结构。

## Agent 掌握的事实

改写只改写法，不增加事实（R25）。改写后的每个事实都来自本节。本节列出的是本虚构示例提供的事实。

- 用户的要求：修复登录后偶发退出的问题。用户没有要求改日志和重试逻辑。
- Agent 读了 `auth/refresh.ts`。第 42 行在刷新前不检查是否已有刷新在进行。
- 两个请求同时刷新 token 时，后完成的刷新使先拿到的 token 失效。
- Agent 修改了 `auth/refresh.ts`：同一时间只发一个刷新请求，其他请求等待这次刷新的结果。
- Agent 删除了 `auth/logger.ts` 中的 3 处重复日志。
- Agent 新增了并发刷新测试，位置是 `auth/refresh.test.ts:88`。
- `npm test auth` 的输出：48 项通过，0 项失败。新增的测试在其中。
- 本机没有 iOS 构建环境。本次没有执行 iOS 端检查。

## 改写前

> 好的，我先看了一下登录相关的代码，发现问题应该是出在 token 刷新的逻辑上，大概是并发的时候两个请求同时去刷新导致的。然后我对 `auth/refresh.ts` 进行了修改，加了一个锁来实现串行化处理，另外顺手把一些日志之类的也优化了一下。测试基本都跑过了，应该没什么问题，不过 iOS 那边因为没有环境暂时没法验证。你看要不要我再把重试逻辑也一起改了？

不合格之处：

- 第一句不是结论（R18）。
- 叙述过程：「我先……然后……」（R21）。
- 「应该」「大概」掩盖不确定（R24）。
- 「进行了修改」「实现串行化处理」是虚化动词（R3）。
- 「日志之类」是开放式列举（R17）。改动也超出了范围。
- 「基本都跑过了」不是固定状态词，没有写出检查方法（R19、R20）。
- 最后的问题主动扩大修改范围，没有说明为什么需要修改重试逻辑或会影响什么。用户尚未要求这项修改。

## 改写后

已完成：登录刷新逻辑的代码修改。iOS 端未验证。

**原因**：两个请求同时刷新 token。后完成的刷新使先拿到的 token 失效。

**证据**：

- `auth/refresh.ts:42` — 刷新前不检查是否已有刷新在进行。

**改动**

- `auth/refresh.ts`：同一时间只发一个刷新请求。其他请求等待这次刷新的结果。
- `auth/logger.ts`：删除 3 处重复日志。这项改动不在原范围内。

**验证**

- 已验证：`npm test auth` — 48 项通过，0 项失败。包含新增并发刷新测试 `auth/refresh.test.ts:88`。
- 未验证：iOS 端 — 本次没有执行 iOS 端检查。本机没有 iOS 构建环境。

**待确认**

- 是否保留 `auth/logger.ts` 的改动：
  1. 撤回（推荐）— 本次提交只含登录修复。
  2. 保留 — 日志清理和登录修复一起提交。

## 说明

- 本示例合并了两个模板：结果汇报加入了排查结论的「原因」节和「证据」节。
- 首句只声明代码修改已完成，不声明整项修复已完成。事实写明「本次没有执行 iOS 端检查」，因此 iOS 端写「未验证」。仅凭本机缺少构建环境，不能得出 iOS 端未验证的结论。若 iOS 检查属于验收条件，整项任务只能写「部分完成」。
- 改写前的「测试基本都跑过了」没有写出检查方法。改写后的数字来自「Agent 掌握的事实」，不是改写时补充的。缺少检查记录时，必须写「未确认」及确认方法；已知没有执行检查时，才写「未验证」。
- 新增并发刷新测试包含在 `npm test auth` 中，因此集中列一次验证结果。
- 「重试逻辑」只是 Agent 主动提出的新工作，用户没有要求。改写后删除这个问题；当前任务不需要用户决定是否修改重试逻辑。
- 超出范围的改动必须在「改动」中标明，并让用户决定。
